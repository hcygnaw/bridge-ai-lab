## 为什么这样造

1. **小水沟**：把路面本身当成受拉的悬带，不另铺第二层桁架。最难的是车辆冲进下坡后腾空，再砸回悬带；用入口信号改变入桥速度，比添加一整排腹杆省钱。
2. **大峡谷**：两岸的三角木桥肩缩短柔性跨，路面、分段索和木弦共同受拉。右侧的灯放在桥肩上，让 2200 kg 超载面包车在进入悬跨前才重新起步；小轿车方向不需要设灯。
3. **早高峰**：把长跨分成两段木桁架，荷载送到两岸和中间礁石。压杆缩短并加侧撑，路面兼作上弦；让一侧车队等另一侧先过，比按两个车队同时压到桥心的工况加钢省钱。
4. **过船**：两个半跨在中间铰接，右端由短摇臂和横向液压杆定位。推近两端就能让中铰下沉，整段航道净空；船走后拉平，再按方向放车。检查的是整根杆与船窗的交集，而不只是路面节点。
5. **钱不够**：没有另修坑桥和河桥。坑内的短斜路面由导杆保持姿态，光电门触发一根液压杆，趁车轮在板上时将车送过河，再回到接车位置。单车飞到对岸还不够，必须实测第二、第三辆的复位和落地。
6. **地狱关**：礁石承担两侧引桥端部的反力，两缸共同悬吊中央桁架；先把完整中跨降到船底以下，复位后分向放行。反复试了无塔吊耳、单缸折桥和双叶桥，保留的是三种交通组合都能承受卡车的设计，不是空载动作最漂亮的设计。
7. **攻防**：静态桥用双塔斜拉，另设钢制后拉路径并加强塔脚。标准车队基线外，七款自制集中配重、不同轴距或活动配重车上桥后，后续车队都能通过；这八次测试的桥体断杆数均为零。捣蛋车用车内液压移动配重；筛选时同时要求自己按时到达和后续车队失败，而不是只数断了几根杆。

## 规则理解和模拟器观察

- 设计格式部分没有突出写明“不能直接连接两个固定锚点”；`check` 会明确拒绝这种杆件。所有提交均以正式解析器的检查为准。
- 航道包含边界，所以设计留了净空余量，不依靠杆件刚好擦边。允许桥构件在运动中进入地形，并不表示车轮也可以穿过去。
- 接近断裂阈值时，小幅改变接缝、落地角度或放行相位，就可能换一根杆先断，后续结果差很多。对固定 JSON 的复跑可重现；没有证据表明这是不确定性或裁判错误。
- 中文 README 列出了 `bridge_sim.exe`，本工作树起初并没有该二进制；按英文 README 用随仓库提供的构建脚本生成本机内核（SHA-256 前 12 位：`8ed818dea867`），未修改物理、校验器或关卡。没有发现可确认的模拟器缺陷。

从 `bridge/workspace` 运行 `python lab/verify.py` 可按交卷文件名重新检查全部正式场景、决赛基线及自对局；单看任一关可用 `python bridge.py run 6 submission/level6.json` 这样的原生命令。保留的构型和降本脚本在 `lab/search/`，例如 `PYTHONPATH=. python lab/search/polish.py 2 60 17` 会试调第 2 关 60 秒，有更便宜的全过解才替换交卷文件；只想复核时不要运行搜索。
